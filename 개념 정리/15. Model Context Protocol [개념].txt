MCP란? 도구 연결의 표준
- Model Context Protocol: AI Agent가 외부 도구(API, DB, 파일 등)를 표준화된 방식으로 연결하기 위한 프로토콜
- MCP Host(우리 앱, Agent) -> MCP Client(통신 담당) -> MCP Server(도구 제공, gitHub)
- 공구 대여점 비유: MCP 서버(공구 대여점), MCP Client(공구 빌리러 온 사람), 설정 파일(대여점 주소록)
- 헷갈리면 안되는 게 Agent가 그냥 도구가 아니라 외부에 있는 도구, 범용성이 있지 않는 도구들을 표준화된 방식으로 연결하기 위한 프로토콜이다. Agent는 MCP 프로토콜만 구축하는거지, MCP 툴을 구축하는 게 아니다.
- 즉, MCP는 Model Context Protocol로 연결하기 위한 프로토콜을 만드는 것이다. 그 외에 도구는 해당 프로그램에서 직접 만들어줘야 한다.

JSON-RPC 2.0: 통신 규약
- MCP는 JSON-RPC 2.0 프로토콜로 메시지를 주고받는다.
- JSON 형태로 "이 메서드를 이 파라미터로 실행해줘"라고 요청하는 표준 규격
- 왜 JSON-RPC
- 1. 단순하고 가벼움
- 2. 언어/플랫폼 무관 -> JSON만 보내면 됨
- 3. id로 요청-응답 매칭 -> 비동기 처리에 유리
- 비유: 공구 대여점과 대화할 때 쓰는 양식 -> 정해진 양식으로 요청하고, 같은 양식으로 답변을 받는 것

설정 파일: 공구 대여점 주소록
- Agent가 MCP 서버를 자동으로 찾아내는게 아니다
- 설정 파일에 MCP 서버 목록을 미리 등록해놓고, Agent가 시작할 때 이 목록을 읽어서 연결을 시작한다
- 비유: 공구 대여점을 찾아 나서는 게 아니라, 주소록에 적어놓은 대여점에 전화를 거는 것

1단계 initialize: 악수
- 설정 파일에서 읽은 각 MCP 서버 URL로 initialize 요청을 보낸다
- Client(Agent)가 Server 에게 "나는 이런 클라이언트야, 이런 기능을 지원해" 보내면 Server는 Client 에게 "나도 이런 기능을 지원해, 프로토콜 버전은 이거야"라고 보낸다
- 서로의 protocolversion 확인, 서로의 capabilities (지원 기능) 교환
- 이 악수가 끝나야 이후 요청 가능
- 비유: 대여점에 들어가서 "안녕하세요, 저는 이런 사람이에요" 하고 인사를 나누는 과정. 인사가 끝나야 도구를 빌릴 수 있다

2단계 tools/list: 도구 목록 받기
- initialize 완료 후, 서버에 "어떤 도구들을 갖고 있어?"라고 요청을 보낸다
- 1. Agent -> Server: "tools/list" 요청
- 2. Server -> Agent: 보유 도구 목록 반환
- 3. Agent: 받은 도구를 내 Tool 목록에 등록
- 4. Claude에게 "이런 도구들도 쓸 수 있어" 전달
- MCP 서버가 여러 개라면 각 서버에서 도구 목록을 받아서 -> 전부 합쳐서 Claude에게 하나의 도구 목록으로 제공
- 참고로 1단계에서 Server가 기능 지원이 없다고 한다면 2단계는 생략

3단계 tools/call: 도구 실행 요청
- Claude가 응답 중 MCP 서버의 도구를 사용하겠다고 하면, Agent가 중간 다리 역할을 수행
- Claude: "이 도구를 이 파라미터로 써줘"
- Agent: "이건 MCP 서버의 도구네", MCP 서버로 tools/call 요청 전달
- MCP 서버: 도구를 실제로 실행하고 결과 반환
- Agent: Claude에게 결과를 돌려줌
- Claude <-> Agent <-> MCP SERVER

로컬 도구 vs MCP 도구
- 예시: web_serach..    |    github_list_issues...
- 실행 주체: Agent가 직접 질행   |    Agent가 MCP 서버에 위임
- 통신: 내부 함수 호출    |     JSON-RPC 2.0 네트워크 통신
- Claude 관점: 차이 없음 -> 둘 다 동일한 도구 목록에 나란히 존재
