Compact
- 전에 대화했던 내용들이 넘쳐날수록 컨텍스트 윈도우의 자리는 부족해진다
- 지금까지 대화했던 내용이 넘쳐서 부족해지면 요약해서 압축을 하자
- Compact -> 메모지를 한 장짜리 요약본으로 정리
- 쌓인 내용 전체를 읽고 핵심만 추출
- 한 장짜리 요약본으로 만듦
- 나머지 내용은 전부 치움
- 요약본 덕분에 핵심 맥락은 유지
- 빈 책상에 새 메모지를 놓을 공간 확보

요약 방향을 사용자가 조절할 수 있다
- ex) /compact -> 전체를 균등하게 요약
- ex) /compact UI 관련 작업 위주로 -> UI 관련 맥락을 우선 보존, 나머지는 더 압축
- ex) /compact 에러 해결 과정 위주로 -> 어떤 에러가 있었고 어떻게 해결했는지 중심으로 요약
- 다음 작업에 필요한 맥락을 선택적으로 남길 수 있음

요약본은 구조화되어 있다
- 단순히 "대화를 줄여줘"가 아니라, 작업을 이어가기 위한 체계적인 요약
- 사용자의 핵심 요청과 의도, 주요 기술적 결정과 패턴, 수행한 작업 내역, 발생한 에러와 해결 방법, 사용자의 피드백과 수정 지시, 아직 남은 작업 목록
- 핵심: 요약본만 보고도 새로운 Claude가 이어서 작업할 수 있을 정도로 충분한 정보

역설: Compact도 컨텍스트를 쓴다
- 요약하려면 기존 히스토리 전체를 Claude에게 보내야 함
- 즉, 요약 요청 자체도 컨텍스트를 사용
- 이미 완전히 꽉 찼다면? 요약 요청조차 보낼 수 없다
- 그래서, 꽉 차기 전에 미리 Compact를 해야 한다
- 너무 늦으면 /clear (전체 초기화)밖에 답이 없다!

주의: Compact는 완벽한 기억이 아니다
- Compact는 요약이지, 원본 보존이 아님
- 정확한 코드, 구체적인 수치, 중간 시행착오의 디테일은 빠질 수 있음
- 50턴의 대화를 한 장으로 줄이는 것 -> 정보 손실은 불가피
- 사용자 지시 요약을 쓰면 특정 부분은 살리지만, 나머지는 더 많이 잘려 나감
- Compact 후 "아까 그거 뭐였지?" -> 모를 수 있음
- 안전한 습관으로 중요한 정보는 Compact 전에 별도로 저장

핵심 정리
- 대화가 길어지면 컨텍스트 윈도우가 꽉 찬다
- Compact는 메모지를 요약본 한 장으로 정리
- 사용자 지시로 요약 방향을 조절 가능
- 꽉 차기 전에 미리 실행해야 함
- Compact는 완벽한 보존이 아닌 실용적 타협이다 -> 맥락은 유지하면서 공간을 확보하되, 세부 디테일 손실은 감수
